# Building a Production-Ready Job Queue with Upstash Redis and Next.js

We had a problem. Our AI content generation system was spawning **dozens of concurrent jobs** across three different pipelines (blogs, resources, newsletters). We needed:

- **Priority ordering** (critical jobs first)
- **Fair scheduling** (don't starve low-priority work)
- **Real-time tracking** (show progress to admins)
- **Fault tolerance** (retry failed jobs)
- **Zero infrastructure** (serverless-first)

Traditional solutions like Bull/BullMQ required a persistent Redis instance. We wanted **serverless**.

Enter **Upstash Redis** + custom job queue.

## Implementation: The JobQueue Class

Here's the core implementation in `/lib/upstash.ts`:

```typescript
import { Redis } from '@upstash/redis'

const redis = new Redis({
  url: process.env.UPSTASH_REDIS_REST_URL!,
  token: process.env.UPSTASH_REDIS_REST_TOKEN!
})

export interface QueueJob {
  id: string
  type: 'blog' | 'resource' | 'newsletter'
  status: 'queued' | 'processing' | 'completed' | 'failed'
  priority: number  // 1 (highest) to 5 (lowest)
  payload: any
  createdAt: string
  startedAt?: string
  completedAt?: string
  error?: string
  retries: number
  maxRetries: number
}

export class JobQueue {
  private queueKey = 'jobs:queue'

  // Enqueue a new job
  async enqueue(job: Omit<QueueJob, 'id' | 'status' | 'createdAt'>): Promise<string> {
    const id = `job:${Date.now()}:${Math.random().toString(36).slice(2)}`

    const queueJob: QueueJob = {
      ...job,
      id,
      status: 'queued',
      createdAt: new Date().toISOString(),
      retries: 0,
      maxRetries: job.maxRetries || 3
    }

    // Add to sorted set (score = negative priority for descending order)
    await redis.zadd(this.queueKey, {
      score: -job.priority,
      member: id
    })

    // Store job metadata (expires in 24 hours)
    await redis.set(`job:${id}`, JSON.stringify(queueJob), { ex: 86400 })

    return id
  }

  // Dequeue next highest priority job
  async dequeue(): Promise<QueueJob | null> {
    // Get highest priority job (lowest score)
    const jobs = await redis.zrange(this.queueKey, 0, 0)

    if (jobs.length === 0) {
      return null
    }

    const jobId = jobs[0]

    // Remove from queue
    await redis.zrem(this.queueKey, jobId)

    // Get job data
    const jobData = await redis.get(`job:${jobId}`)

    if (!jobData) {
      return null
    }

    const job = JSON.parse(jobData as string) as QueueJob

    // Update status to processing
    job.status = 'processing'
    job.startedAt = new Date().toISOString()

    await redis.set(`job:${jobId}`, JSON.stringify(job), { ex: 86400 })

    return job
  }

  // Mark job as completed
  async complete(jobId: string): Promise<void> {
    const jobData = await redis.get(`job:${jobId}`)

    if (!jobData) {
      throw new Error(`Job ${jobId} not found`)
    }

    const job = JSON.parse(jobData as string) as QueueJob
    job.status = 'completed'
    job.completedAt = new Date().toISOString()

    await redis.set(`job:${jobId}`, JSON.stringify(job), { ex: 86400 })
  }

  // Mark job as failed and optionally retry
  async fail(jobId: string, error: string): Promise<boolean> {
    const jobData = await redis.get(`job:${jobId}`)

    if (!jobData) {
      throw new Error(`Job ${jobId} not found`)
    }

    const job = JSON.parse(jobData as string) as QueueJob
    job.error = error
    job.retries += 1

    // Retry if under max retries
    if (job.retries < job.maxRetries) {
      job.status = 'queued'

      // Re-enqueue with lower priority (original priority + retries)
      await redis.zadd(this.queueKey, {
        score: -(job.priority - job.retries),
        member: jobId
      })

      await redis.set(`job:${jobId}`, JSON.stringify(job), { ex: 86400 })

      return true // Retrying
    }

    // Max retries exceeded
    job.status = 'failed'
    job.completedAt = new Date().toISOString()

    await redis.set(`job:${jobId}`, JSON.stringify(job), { ex: 86400 })

    return false // Failed permanently
  }

  // Get queue stats
  async getStats() {
    const queueSize = await redis.zcard(this.queueKey)

    // Get all job IDs from queue
    const jobIds = await redis.zrange(this.queueKey, 0, -1)

    const jobs = await Promise.all(
      jobIds.map(async (id) => {
        const data = await redis.get(`job:${id}`)
        return data ? JSON.parse(data as string) : null
      })
    )

    const validJobs = jobs.filter(Boolean) as QueueJob[]

    const byPriority = validJobs.reduce((acc, job) => {
      acc[job.priority] = (acc[job.priority] || 0) + 1
      return acc
    }, {} as Record<number, number>)

    const byType = validJobs.reduce((acc, job) => {
      acc[job.type] = (acc[job.type] || 0) + 1
      return acc
    }, {} as Record<string, number>)

    return {
      queueSize,
      byPriority,
      byType,
      oldestJob: validJobs[validJobs.length - 1]?.createdAt,
      newestJob: validJobs[0]?.createdAt
    }
  }
}

export const jobQueue = new JobQueue()
```

## Key Design Decisions

### 1. **Sorted Sets for Priority Queue**

Redis sorted sets are **perfect** for priority queues:

```typescript
// Add job with priority 1 (highest)
await redis.zadd('jobs:queue', {
  score: -1,  // Negative for descending order
  member: 'job:123'
})

// Get highest priority job
const [jobId] = await redis.zrange('jobs:queue', 0, 0)
```

**Why negative scores?** Redis sorted sets default to ascending order. We want **highest priority first**, so we negate the priority value.

### 2. **Separate Storage for Job Metadata**

```typescript
// Queue only stores job IDs (lightweight)
jobs:queue → Sorted Set of job IDs

// Metadata stored separately (can be large)
job:123 → Hash of full job data
```

This keeps the sorted set **small and fast**.

### 3. **TTL for Auto-Cleanup**

```typescript
await redis.set(`job:${id}`, JSON.stringify(job), {
  ex: 86400  // Expire after 24 hours
})
```

Old jobs automatically disappear. No manual cleanup needed.

### 4. **Retry Logic with Exponential Backoff**

```typescript
if (job.retries < job.maxRetries) {
  // Lower priority on retry (priority + retries)
  await redis.zadd(this.queueKey, {
    score: -(job.priority - job.retries),
    member: jobId
  })
}
```

Failed jobs get **re-queued with lower priority** so they don't block new work.

## Worker Implementation

```typescript
// lib/workers/job-worker.ts
import { jobQueue } from '@/lib/upstash'
import { generateBlogPost } from '@/lib/services/blog-generator'
import { generateResource } from '@/lib/services/resource-generator'
import { generateNewsletter } from '@/lib/services/newsletter-generator'

export async function processNextJob() {
  // Dequeue next job
  const job = await jobQueue.dequeue()

  if (!job) {
    console.log('[Worker] No jobs in queue')
    return
  }

  console.log(`[Worker] Processing job ${job.id} (type: ${job.type}, priority: ${job.priority})`)

  try {
    switch (job.type) {
      case 'blog':
        await generateBlogPost(job.payload)
        break
      case 'resource':
        await generateResource(job.payload)
        break
      case 'newsletter':
        await generateNewsletter(job.payload)
        break
      default:
        throw new Error(`Unknown job type: ${job.type}`)
    }

    // Mark as completed
    await jobQueue.complete(job.id)
    console.log(`[Worker] Completed job ${job.id}`)

  } catch (error) {
    console.error(`[Worker] Job ${job.id} failed:`, error)

    const willRetry = await jobQueue.fail(job.id, String(error))

    if (willRetry) {
      console.log(`[Worker] Job ${job.id} will retry (attempt ${job.retries + 1}/${job.maxRetries})`)
    } else {
      console.log(`[Worker] Job ${job.id} failed permanently`)
    }
  }
}
```

**Running the worker**:

```typescript
// Continuous polling
setInterval(async () => {
  await processNextJob()
}, 5000)  // Check every 5 seconds
```

Or use a **cron job** (Vercel Cron, GitHub Actions, etc.):


## Lessons Learned

### 1. **Keep Jobs Small**
Large payloads slow down Redis operations. Store job data in Postgres, pass only IDs in queue.

```typescript
// ❌ Bad: Large payload
await jobQueue.enqueue({
  type: 'blog',
  payload: { researchData: '...10KB of text...' }
})

// ✅ Good: Lightweight reference
await jobQueue.enqueue({
  type: 'blog',
  payload: { topicId: 'abc123' }  // Worker loads full data from DB
})
```

### 2. **Retries Need Exponential Backoff**
Linear retries can cause cascading failures.

```typescript
// Priority decreases by retry count
score: -(job.priority - job.retries)

// Job with priority 1:
// Attempt 1: score = -1
// Attempt 2: score = 0
// Attempt 3: score = 1
```

### 3. **Monitor Queue Depth**
Set alerts when queue grows too large:

```typescript
const stats = await jobQueue.getStats()

if (stats.queueSize > 100) {
  await sendAlert('Queue backlog: ' + stats.queueSize + ' jobs')
}
```

### 4. **Dead Letter Queue**
Move permanently failed jobs to a separate queue for manual review:

```typescript
if (!willRetry) {
  await redis.zadd('jobs:dead-letter', {
    score: Date.now(),
    member: job.id
  })
}
```

## Comparison: Bull/BullMQ vs Upstash

| Feature | Bull/BullMQ | Upstash |
|---------|-------------|---------|
| Infrastructure | Persistent Redis required | Serverless |
| Deployment | Docker/EC2/managed Redis | HTTP API |
| Cost | $15-50/month | $0-10/month |
| Latency | 5-20ms | 50-100ms |
| Features | Advanced (rate limiting, repeatable jobs) | Basic (queue, retry) |
| Complexity | High | Low |

**Our verdict**: Upstash wins for **serverless-first** Next.js apps. Use Bull if you need advanced features or have existing Redis infrastructure.
