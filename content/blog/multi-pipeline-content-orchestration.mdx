# Orchestrating 3 Parallel Content Pipelines: Blogs, Resources, and Newsletters at Scale

We built **three separate content generation pipelines** that run **simultaneously** without stepping on each other's toes:

1. **Blog Pipeline**: Technical articles with research → outline → draft → QA
2. **Resource Pipeline**: Educational guides with topic discovery → generation → publishing
3. **Newsletter Pipeline**: Weekly digests with content aggregation → scheduling → sending

Each pipeline has its own:
- Database tables (Prisma models)
- API endpoints (Next.js routes)
- Admin UI (React components)
- Real-time monitoring (SSE streams)
- Job queue (Upstash Redis)

Here's how we orchestrated them to work in harmony.

## The Challenge

### Initial Problem
We started with a single blog generation script. It worked. Then we added resource articles. Then newsletters. Then topic discovery. Then automated research.

Before we knew it, we had:
- **15 database tables** with overlapping concerns
- **30+ API endpoints** with duplicate logic
- **No coordination** between pipelines
- **Race conditions** when updating shared state
- **No visibility** into what's running where

We needed **architecture**.

## Pipeline Architecture

### 1. Blog Pipeline

**Phases**: Topic Discovery → Research → Outline → Draft → QA → Publish

## Coordinated State Management

### Problem: Shared State Updates

Multiple pipelines update shared resources:
- Generation jobs table
- User activity logs
- System metrics

**Race condition example**:
```typescript
// ❌ BROKEN: Two pipelines updating same job
// Blog worker
const job = await prisma.generationJob.findUnique({ where: { id: jobId } })
job.itemsProcessed += 1
await prisma.generationJob.update({ where: { id: jobId }, data: job })

// Resource worker (running simultaneously)
const job = await prisma.generationJob.findUnique({ where: { id: jobId } })
job.itemsProcessed += 1  // Overwrites blog worker's update!
await prisma.generationJob.update({ where: { id: jobId }, data: job })
```

### Solution: Atomic Updates

```typescript
// ✅ FIXED: Atomic increment
await prisma.generationJob.update({
  where: { id: jobId },
  data: {
    itemsProcessed: { increment: 1 }  // Atomic operation
  }
})
```

```typescript
  SELECT
    (SELECT COUNT(*) FROM "BlogPost") as blogCount,
    (SELECT COUNT(*) FROM "ResourceDraft") as resourceCount,
    (SELECT COUNT(*) FROM "NewsletterSent") as newsletterCount
`
```

## Real-Time Monitoring with SSE

Each pipeline has its own SSE stream, but they all use a **shared SSE manager**:

```typescript
// lib/sse-manager.ts
class SSEManager {
  private clients = new Map<string, ReadableStreamDefaultController>()

  registerClient(clientId: string, controller: ReadableStreamDefaultController) {
    this.clients.set(clientId, controller)
  }

  unregisterClient(clientId: string) {
    this.clients.delete(clientId)
  }

  broadcast(pipeline: 'blog' | 'resource' | 'newsletter', event: any) {
    const message = `data: ${JSON.stringify({ pipeline, ...event })}\n\n`
    const encoder = new TextEncoder()

    // Send to all clients subscribed to this pipeline
    for (const [clientId, controller] of this.clients.entries()) {
      if (clientId.startsWith(pipeline)) {
        try {
          controller.enqueue(encoder.encode(message))
        } catch (e) {
          console.error(`Failed to send to client ${clientId}:`, e)
          this.unregisterClient(clientId)
        }
      }
    }
  }
}

export const sseManager = new SSEManager()
```

**Usage in generators**:
```typescript
// Blog generator
sseManager.broadcast('blog', {
  type: 'progress',
  message: 'Generating outline...',
  progress: 25
})

// Resource generator
sseManager.broadcast('resource', {
  type: 'progress',
  message: 'Researching topic...',
  progress: 50
})

// Newsletter generator
sseManager.broadcast('newsletter', {
  type: 'progress',
  message: 'Compiling sections...',
  progress: 75
})
```

**Client-side**:

**Worker processes jobs in priority order**:
```typescript
async function processNextJob() {
  const job = await jobQueue.dequeue()  // Gets highest priority job

  switch (job.type) {
    case 'newsletter-generate':
      await generateNewsletter(job.payload)
      break
    case 'blog-research':
      await researchBlogTopic(job.payload)
      break
    case 'resource-generate':
```

## Error Handling and Recovery

### Problem: Pipeline-Specific Errors

Each pipeline has unique failure modes:
- **Blogs**: Outline generation fails → retry with simpler prompt
- **Resources**: Research insufficient → mark for manual review
- **Newsletters**: Send fails → schedule retry at next optimal time

**Centralized error handler**:
```typescript
// lib/error-handler.ts
export async function handleGenerationError(
  pipeline: 'blog' | 'resource' | 'newsletter',
  error: Error,
  jobId: string
) {
  // Log error
  console.error(`[${pipeline}] Job ${jobId} failed:`, error)

  // Pipeline-specific recovery
  switch (pipeline) {
    case 'blog':
      // Retry with fallback prompt
      if (error.message.includes('outline')) {
        await retryWithSimplifiedPrompt(jobId)
      }
      break

    case 'resource':
      // Mark for manual review
      if (error.message.includes('research')) {
        await markForManualReview(jobId)
      }
      break

    case 'newsletter':
      // Delay and retry
      if (error.message.includes('send')) {
        await scheduleRetry(jobId, 3600)  // Retry in 1 hour
      }
      break
  }

  // Broadcast error to SSE clients
  sseManager.broadcast(pipeline, {
    type: 'error',
    message: error.message,
    jobId
  })
}
```

## Lessons Learned

### 1. **Separate Pipelines = Independent Failures**

When blog pipeline breaks, resources and newsletters keep running.

**Before** (monolithic):
```typescript
// Single generator for all content
async function generateContent(type, payload) {
  if (type === 'blog') { ... }
  else if (type === 'resource') { ... }
  else if (type === 'newsletter') { ... }
}
// Bug in blog logic breaks ALL content generation
```

**After** (isolated):
```typescript
// Separate generators
await generateBlogPost(payload)
await generateResource(payload)
await generateNewsletter(payload)
// Blog bug doesn't affect resources or newsletters
```

### 2. **Atomic Updates for Shared State**

Use Prisma's atomic operations:
```typescript
// Increment
data: { count: { increment: 1 } }

// Decrement
data: { count: { decrement: 1 } }

// Multiply
data: { count: { multiply: 2 } }
```

### 3. **Single SSE Manager for All Pipelines**

Sharing an SSE manager reduces memory usage and simplifies monitoring.

### 4. **Pipeline-Specific Error Handlers**

Different pipelines need different recovery strategies. Centralize the error handling logic but customize per pipeline.

### 5. **Prioritize Time-Sensitive Work**

Newsletters have hard deadlines (scheduled sends). Always give them highest priority.

## Takeaway

Building multiple content pipelines doesn't mean building three separate systems. With **shared infrastructure** (SSE manager, job queue, error handler) and **pipeline-specific logic** (generators, APIs, error recovery), you can orchestrate complex workflows while keeping your codebase **DRY** and **maintainable**.

Key principles:
- Separate pipelines = isolated failures
- Shared infrastructure = reduced duplication
- Atomic updates = no race conditions
- Priority queue = optimal resource usage
- Real-time monitoring = visibility into all pipelines
