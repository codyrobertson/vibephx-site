# State Management at Scale: Fixing Race Conditions in Our Admin Dashboard

We had a problem. Our admin dashboard showed **"4 topics in queue"** even after approving all of them. Refreshing the page didn't help. The database showed the right status, but the UI was stuck.

This is the story of how we debugged a gnarly state synchronization bug in a multi-queue content generation system and learned some hard lessons about single sources of truth.

## The System

We built three parallel content pipelines:

```
Resource Articles Pipeline:
  Topics → Queue → Research → Generate → Draft → Publish

Blog Posts Pipeline:
  Topics → Queue → Research → Outline → Draft → QA → Publish

Newsletter Pipeline:
  Drafts → Schedule → Generate → Send
```

Each pipeline has:
- **Database tables** (source of truth)
- **API endpoints** (read/write operations)
- **Admin UI** (React components with state)
- **Real-time updates** (SSE streams)

## The Bug

User workflow:

1. Click "Approve All Topics" (4 topics)
2. Topics disappear from approval UI ✅
3. Navigate to Resources admin page
4. **Bug**: Stats show "4 Queued" but queue is empty
5. Refresh page → Still shows "4 Queued"
6. Check database → All topics marked `COMPLETED`

**WTF?** The database is correct, but the UI is wrong.

## Root Cause: Missing Database Filter

The API was fetching ALL topics, then the UI filtered by status:

```typescript
// ❌ BROKEN: API returns everything
export async function GET() {
  const topics = await prisma.resourceTopic.findMany({
    orderBy: [
      { priority: 'desc' },
      { createdAt: 'desc' }
    ],
    take: 50
  })
  return NextResponse.json({ topics })
}
```

```typescript
// ❌ BROKEN: UI filters client-side
const queuedTopics = topics.filter(t => t.status === 'QUEUED')
const completedTopics = topics.filter(t => t.status === 'COMPLETED')
```

**Problem**: After approval, topics change to `COMPLETED` in the database. But the UI still has them in memory as `QUEUED` until the next refresh.

Even worse: when we DID refresh, the API returned ALL topics (including completed ones), so the count was still wrong.

## The Fix: Filter at Query Time

```typescript
// ✅ FIXED: API excludes completed topics
export async function GET() {
  const topics = await prisma.resourceTopic.findMany({
    where: {
      status: {
        not: 'COMPLETED'  // Only return active topics
      }
    },
    orderBy: [
      { priority: 'desc' },
      { createdAt: 'desc' }
    ],
    take: 50
  })
  return NextResponse.json({ topics })
}
```

Now the UI stats are correct:

```typescript
const queuedTopics = topics.filter(t => t.status === 'QUEUED')
// Only includes actual queued topics

const completedTopics = topics.filter(t => t.status === 'COMPLETED')
// Always empty (completed topics not returned by API)
```

**Lesson**: **Single source of truth**. Filter in the database query, not in the UI.

## Bug #2: Approval State Race Condition

After fixing the API, we found another bug:

**Steps**:
1. User approves 4 topics
2. UI updates immediately (optimistic)
3. API call happens in background
4. User navigates to Resources page
5. Topics still showing as `QUEUED` instead of `APPROVED`

**Root cause**: The approval API was updating `status` but not `addedBy`:

```typescript
// ❌ BROKEN: Only updates status
await prisma.resourceTopic.update({
  where: { id: topicId },
  data: {
    status: 'QUEUED'  // Changed from PENDING to QUEUED
  }
})
```

But the Resources page was filtering by `addedBy`:

```typescript
const queuedTopics = topics.filter(t =>
  t.status === 'QUEUED' && t.addedBy === 'approved'
)
```

Topics had `addedBy: 'auto-discovery'` so they weren't showing up!

## The Fix: Update All Related Fields

```typescript
// ✅ FIXED: Update status AND addedBy
await prisma.resourceTopic.update({
  where: { id: topicId },
  data: {
    status: 'QUEUED',
    addedBy: 'approved',  // Changed from 'auto-discovery'
    notes: topic.notes + `\nApproved by: ${user.email} at ${new Date()}`
  }
})
```

**Lesson**: When changing state, update **all related fields** that other queries depend on.

## Bug #3: Empty Stats After Batch Operations

After approving topics in a batch:

```typescript
// Approve all 4 topics
for (const topicId of approvedIds) {
  await fetch('/api/topics/approve', {
    method: 'POST',
    body: JSON.stringify({ topicId, approved: true })
  })
}

// Navigate to dashboard
router.push('/admin/resources')
```

**Bug**: Stats showed `0 Queued, 0 Generating, 0 Failed`.

**Cause**: The dashboard loaded **before** the approval API calls finished.

**Fix**: Wait for ALL approvals to complete before navigating:

```typescript
// ✅ FIXED: Parallel requests with Promise.all
await Promise.all(
  approvedIds.map(topicId =>
    fetch('/api/topics/approve', {
      method: 'POST',
      body: JSON.stringify({ topicId, approved: true })
    })
  )
)

// Now navigate (all requests done)
router.push('/admin/resources')
```

**Lesson**: Don't navigate away while async operations are in flight. Use `Promise.all()` for parallel requests.

## Bug #4: SSE Connection Closing Prematurely

Our real-time generation stream was disconnecting after 30 seconds:

```
[SSE] Connected
[SSE] Event: Starting generation...
[SSE] Event: Validating topic...
... (30 seconds later)
[SSE] Connection error: NS_BINDING_ABORTED
```

**Cause**: Proxy timeout. Cloudflare/Nginx close idle SSE connections after 30-60s.

**Fix**: Send keepalive pings every 15 seconds:

```typescript
const stream = new ReadableStream({
  start(controller) {
    // Register client
    sseEmitter.registerClient(clientId, controller)

    // ✅ ADDED: Keepalive every 15s
    const keepalive = setInterval(() => {
      try {
        const ping = ': keepalive\n\n'
        controller.enqueue(encoder.encode(ping))
      } catch {
        clearInterval(keepalive)
      }
    }, 15000)

    // Clean up on disconnect
    req.signal.addEventListener('abort', () => {
      clearInterval(keepalive)
      sseEmitter.unregisterClient(clientId)
    })
  }
})
```

**Lesson**: For long-lived connections, send periodic keepalive messages to prevent proxy timeouts.

## Principles for State Management

### 1. Single Source of Truth

**Bad**: Multiple filters across layers

```typescript
// API filters
const topics = await prisma.resourceTopic.findMany({
  where: { status: { not: 'COMPLETED' } }
})

// UI ALSO filters
const active = topics.filter(t => t.status !== 'COMPLETED')
```

**Good**: Filter once, at the source

```typescript
// API filters
const topics = await prisma.resourceTopic.findMany({
  where: { status: { not: 'COMPLETED' } }
})

// UI trusts the data
const active = topics  // No filtering needed
```

### 2. Update All Related State

When changing one field, update all dependent fields:

```typescript
// ❌ Partial update
await prisma.topic.update({
  data: { status: 'QUEUED' }
})

// ✅ Complete update
await prisma.topic.update({
  data: {
    status: 'QUEUED',
    addedBy: 'approved',  // Also update source
    approvedAt: new Date(),  // Track when
    approvedBy: user.id  // Track who
  }
})
```

### 3. Wait for Async Operations

```typescript
// ❌ Race condition
topicIds.forEach(async (id) => {
  await updateTopic(id)
})
router.push('/dashboard')  // Might run before updates finish!

// ✅ Wait for completion
await Promise.all(
  topicIds.map(id => updateTopic(id))
)
router.push('/dashboard')  // All updates done
```

### 4. Optimistic Updates Need Rollback

```typescript
// Optimistically update UI
setTopics(topics.filter(t => t.id !== deletedId))

// Call API
const res = await fetch('/api/topics/delete', { ... })

// ❌ If it fails, UI is wrong
if (!res.ok) {
  // Need to rollback!
  setTopics(prevTopics)  // But we lost the original state
}

// ✅ Better: Keep original state for rollback
const originalTopics = topics
setTopics(topics.filter(t => t.id !== deletedId))

const res = await fetch('/api/topics/delete', { ... })
if (!res.ok) {
  setTopics(originalTopics)  // Rollback to original
  toast.error('Delete failed')
}
```

### 5. Server State is Truth

If server and client disagree, **server wins**:

```typescript
useEffect(() => {
  // Always refresh on mount
  loadDataFromServer()
}, [])

// Don't rely on cached/stale client state
```

## The Checklist

When building multi-state systems:

- [ ] Filter data at the database level, not in UI
- [ ] Update all related fields when changing state
- [ ] Wait for async operations before navigation
- [ ] Add keepalive for long-lived connections (SSE, WebSockets)
- [ ] Test state transitions with integration tests
- [ ] Log at every layer (DB, API, UI)
- [ ] Use TypeScript to enforce state transitions
- [ ] Document state machine (draw a diagram!)
